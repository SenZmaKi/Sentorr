# Sentorr performance audit — 2 October 2026

The largest measured opportunities are home-page animation CPU and graphics
memory, rather than torrent download CPU. A controlled test preserved the home
page and changed ticker enablement: CPU fell from **14.8% to 0.3%**, then returned
to **13.3%** when tickers resumed. Home physical footprint was **811–878 MiB**
across three runs. A sustained local download averaged **3.1% CPU**; hardware
H.264 torrent playback averaged **24.9% CPU**.

**100% CPU means one fully occupied core**, not the entire M1. These are measured
profile-build results for the audited snapshot, not performance guarantees.

## What was measured

Apple M1, 8 GiB RAM, macOS 27.0; Flutter 3.47.1 / Dart 3.13.1. The main window
stayed hidden and was never focused. No browser inspection was used.

The base source was commit `22d0f214afd072a59f5ad086cb34eb74323ef3e0`.
Concurrent workspace changes broke a follow-up build, so the definitive transfer
run and animation experiment used an isolated archive of that commit with the
profiling harness and an optional bootstrap data-root argument. Later workspace
edits are outside this audit. Three fresh data roots avoided the user's settings,
watch history and downloads.

The harness runs production bootstrap, catalog/search/title screens and download
queue. It scrolls home in twelve 450-pixel steps, searches three terms, opens
three title pages, and expands Batman search from 30 to 60 results. Playback uses
the production engine and `MediaKitTorrentAdapter` in a dedicated video widget;
it does **not** include the full player page or its controls/history integration.

The fixture is a 120-second, 1920×1080, 60 FPS H.264 MP4, about 60.3 MiB, made by
repeating the existing Big Buck Bunny clip. It has no audio. A separate
libtorrent process seeds it over loopback; its CPU and memory are excluded. The
second run limits the seed torrent's upload to 1 MiB/s. Engine DHT/LSD/UPnP/NAT-PMP
are disabled, and the engine is configured eagerly even when initially empty.
Real internet peer discovery and normal lazy engine startup are therefore not
represented.

CPU comes from one-second deltas of process CPU time. RSS comes from `ps` and
Dart `ProcessInfo`; `vmmap` provides separate physical-footprint snapshots.
Native three-second stack samples identify executing/waiting paths. VM-service
heap snapshots were collected in runs 2 and 3. Live IMDb responses succeeded.
The host had other processes running and substantial compression; CPU and memory
vary between runs. Profiling tools also add overhead.

The download received about **21 MiB in 25 seconds**, with sampled rates rising
to approximately 1 MiB/s. It remained incomplete during the window, so this is
actual sustained transfer. Pause retained the torrent; cancellation removed its
download ownership before a fresh streaming directory was used.

Playback progressed beyond two seconds with 1920-pixel decoder output. Both
full runs reported **`hwdec-current=videotoolbox`** and **zero decoder frame
drops** at the ending snapshot. The second run took roughly 18–20 seconds from
stream preparation to the two-second playback check, versus roughly four
seconds with the faster first seed. This is consistent with the configured
initial cache wait and slower delivery, but does not isolate each component of
startup time. Seeking was issued and HTTP stream requests increased from three
to four; seek latency/presented-frame continuity were not independently timed.

The first exploratory run also showed substantial home CPU (29.4%), playback
CPU (20.0%) and home footprint (857 MiB). Its torrent completed within a few
seconds, so its 25-second download average is **not** a sustained-download
benchmark. Its Interstellar pagination was a no-op and is excluded from
pagination conclusions.

## Why the app behaves this way

**The home page continuously renders while apparently idle.**
`FeaturedSection` advances a spotlight and `KenBurns` changes its artwork scale.
Native home samples repeatedly contain `flutter::Rasterizer`/Impeller drawing,
blend/filter and snapshot paths. The theme's effects and the blurred ambient
artwork make repainting more expensive than an unchanged page. Stack samples
include sleeping threads; their counts are not presented as CPU percentages.

Run 3 kept a stable `ValueListenableBuilder`/`TickerMode` widget tree and preserved
the mounted home page:

| Same-page experiment | CPU mean |
| --- | ---: |
| Animated home | 14.8% |
| Tickers disabled | 0.3% |
| Tickers resumed | 13.3% |

This reversible change strongly identifies active UI tickers/rendering as the
main source of this idle CPU cost. Disabling tickers also invokes Flutter's
normal ticker-aware image-listener handling. It does not unmount the page.
Run 2's earlier ticker comparison remounted the app and is excluded from this
causal conclusion.

**Most of the home memory cost is outside the Dart model heap.** The run-2 home
Dart heap samples were approximately 23–28 MiB. In the 811 MiB footprint snapshot,
`owned unmapped (graphics)` accounted for about 481 MiB of allocations,
`IOAccelerator (graphics)` about 134 MiB, and IOSurface about 49 MiB. These are OS
categories, not a precise attribution of every byte to a particular widget.

The Flutter decoded-image cache reached about **100 MiB**. Its default
keep-alive budget is 100 MiB; live image references and graphics resources are
additional. Sentorr's image-cache preference governs **disk files**, not that
whole in-memory footprint. Five featured titles and backdrops are preloaded;
`FadePageStack` preserves main pages, and the title-detail family providers are
not auto-disposed. Keeping these resources improves revisits but has a memory
cost. CDN rendition sizing already exists; this audit does not assume originals
are always downloaded.

Low RSS therefore does not mean a small app. macOS compressed/swapped regions
and graphics ownership explain the large gap between RSS and footprint.
In run 3, disabling tickers barely changed the beginning footprint snapshot
(878 → 873 MiB), despite eliminating most CPU. Animation scheduling and retained
memory need separate treatment.

**Torrent playback intentionally holds several layers of buffers.** The torrent
piece cache reached its **24 MiB** limit and remained bounded in both full runs.
The adapter sets mpv's forward demuxer cap to **64 MiB**, backward cap to
**16 MiB**, a 60-second forward target and a 10-second initial/resume cache wait.
The `PlayerConfiguration` 64 MiB buffer and adapter's 64 MiB demuxer setting
should not be counted as two independent 64 MiB allocations. The engine's
16 MiB read-ahead window schedules pieces; it is not a separate preallocated
16 MiB Dart buffer.

Native pieces are copied into Dart-owned byte arrays, cached, copied into HTTP
response buffers and consumed by mpv. This adds allocation/copy work beyond
simply saving torrent bytes. Hardware decoding reduces video decode cost but
does not eliminate HTTP serving, copies, demuxing, texture uploads or rendering.
These explain why streaming CPU exceeds downloading CPU in this fixture.

**Background polling remains, but it is a smaller measured cost here.** Once the
native session starts, alerts are pumped every 20 ms and full torrent snapshots
are published every 500 ms on the engine worker. The UI consumes immutable
snapshots. Download progress publishes frequently, but the queue persists on
status changes rather than rewriting its file on every progress tick. Empty
engine/static UI CPU was near zero in the controlled experiment; polling is not
the leading optimization suggested by these measurements.

**Close released the stream, but this does not prove absence of leaks.** Torrent
telemetry became empty, the player was disposed, and run-2 Dart heap samples
returned to approximately 25–27 MiB. Footprint remained around 548 MiB at the
post-close snapshot, including the global artwork cache and retained graphics
resources. A longer repeated open/seek/close workload is needed to distinguish
bounded caching/allocator retention from cumulative growth.

A separate **shutdown wait** occurred in run 2 after the workload-complete event:
about **97 recorded seconds** at low CPU before the profiling process was
terminated. The exact awaited operation was not instrumented, so the cause is
unresolved; it is a shutdown/lifecycle finding, not evidence of a busy CPU loop.
Run 3 also stalled during shutdown for over 100 seconds after its final timed
workload, and was terminated. Run 1 exited normally. The current harness bounds
shutdown to 15 seconds and reports a timeout separately. This finding applies
to the audited snapshot.

## Changes worth prioritizing

1. Suspend spotlight/zoom tickers when the window is hidden or minimized; keep
   reduced-motion behavior. Isolate animated artwork repainting from static
   text/cards and profile expensive filter/shadow passes without changing the
   locked visual design. This has the strongest measured CPU evidence.
2. Treat decoded images and graphics memory as explicit budgets separate from
   disk cache size. Revisit preload count, decode dimensions, page retention and
   completed title-provider retention. Verify footprint, not just Dart heap/RSS.
3. Trace the shutdown await with phase timing and a bounded diagnostic harness.
   Confirm the normal app exit path on the latest workspace after ongoing edits.
4. Then benchmark representative movie bitrates, large pieces and repeated seeks
   before tuning the 24/64/16 MiB caches or replacing byte copies. Current bounds
   work in this fixture; no evidence here justifies rewriting the torrent engine.

No optimization changes were applied. The only intended production change for
this audit is an optional `rootDirectory` argument to `AppRuntime.initialize`,
using the existing `AppPaths` isolation support. The default startup is unchanged.
The harness passed scoped Flutter analysis; the profile builds ran successfully.

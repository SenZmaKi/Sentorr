# macOS page memory audit — 2026-10-06

Home is the largest native-memory contributor. Pages were eagerly mounted;
making them lazy corrects unnecessary initialization, but does not explain or
remove most of the measured memory. The macOS renderer has a larger effect.

## What “graphics” means

The measured category is `vmmap`'s **owned unmapped (graphics)** allocation,
not the compressed size of downloaded pictures and not the Dart heap. It can
include native textures and intermediate render buffers. We have not identified
the owner of every allocation, so this category alone cannot prove a GPU leak.

The experimental window had 2,200 × 1,456 physical pixels. One full-size buffer
is approximately 12.2 MiB at four bytes per pixel, or 24.4 MiB at eight bytes.
Multiple surfaces, decoded images, blur intermediates and retained resources
can therefore cost much more than the JPEG files. The installed Flutter engine
uses eight-byte wide-gamut macOS surfaces on the Impeller path and four-byte
standard-color surfaces on the Skia path; this explains part, not all, of the
difference. See [FlutterSurface.mm](https://github.com/flutter/flutter/blob/3.47.1/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterSurface.mm).

## Page isolation

Fresh profile processes, identical window size, isolated application data,
five fixed local artwork fixtures and no active downloads or playback were
used. Home cycled through all five featured titles before measurement.
Animations were disabled for the static comparisons. Each row is the median
of three snapshots after a 30-second warm-up, with GC before heap measurement.
All sizes below are MiB. Graphics is an allocation category, not an additional
amount to add to footprint. Shared isolate-group memory was not double-counted.

| Cold destination / configuration | Physical footprint | Graphics | GC Dart heap |
| --- | ---: | ---: | ---: |
| Blank Flutter view | 79 | ~0 | 15.3 |
| Settings, original eager pages | 293–296 | 123.5 | 19.4 |
| Settings, lazy pages | 296–297 | 123.5 | 18.3 |
| Downloads, lazy pages | 247 | 81.9 | 16.1 |
| Home, lazy pages | 590 | 387.3 | 19.1 |

The original `FadePageStack` mounted Home, Search, Downloads and Settings on
startup. Settings-first now mounts only Settings. Visited pages remain mounted
to preserve their input and scroll state. The first visit still fades in.
Settings's approximately 5.1 MiB image cache is bundled branding, not Home's
fixture artwork. Its graphics footprint therefore remains high even without
Home being created. The short observation showed stable post-GC Dart heaps;
it does not establish absence of a long-running leak.

## Narrowing Home components

| Home exclusion, same Impeller configuration | Footprint | Graphics |
| --- | ---: | ---: |
| Full scene | 590 | 387.3 |
| Ambient background removed | 484 | 293.8 |
| Featured hero artwork removed | 522 | 321.8 |
| All AppImage widgets removed | 459 | 282.0 |

The ambient background and hero are significant contributors. These savings
are not additive. Removing images still leaves substantial native rendering
allocation. Removing surface shadows barely changed graphics allocation;
changing shadow blur style or removing an outer repaint boundary did not
reliably improve it. Those experimental changes were not retained.

Changing Home to a blank view retained much of the allocation. A deliberate
12-frame repaint pump did not release it either (387.3 MiB graphics before and
after). No speculative frame-pump or memory-pressure workaround was shipped.

## Renderer comparison and retained changes

| Lazy destination | Impeller footprint | Skia/Metal footprint | Graphics, Impeller → Skia |
| --- | ---: | ---: | ---: |
| Settings, static | 296–297 | 169 | 123.5 → 29.2 |
| Home, static | 590–630 | 473 | 387.3 → 185.9 |
| Home, animated | 742 | 416 | 379.3 → 207.3 |

The same Home image cache remained approximately 58.4 MiB with either renderer.
The larger reduction is native rendering allocation, not smaller Dart objects.
Total footprint varies more than the graphics category across repeated runs.

Retained changes:

- Lazily mount navigation destinations and preserve visited page state.
- Set the supported `FLTEnableImpeller=false` macOS bundle setting to use
  Skia with Metal. Artwork, ambient effects and theme shadows remain enabled.

This is an engine-specific workaround, not a claim that every allocation has
been fixed. Recheck it after Flutter engine updates. A full native app restart
is required; hot reload does not apply the bundle setting.

**Tradeoff:** the installed engine ties macOS wide-gamut surfaces to Impeller.
Skia uses standard-color surfaces. HDR/wide-gamut fidelity was not validated.
Hidden animation rates were inconsistent between runs (including a Skia run
slower than Impeller); these tests do not justify a frame-rate improvement
claim. Foreground smoothness, sustained playback, seeking and torrent load
remain separate validation work.

## Validation

- Eleven focused page-stack, shell, activity and artwork tests passed.
- Scoped Dart analysis passed; plist lint and diff checks passed.
- The normal `lib/main.dart` macOS profile build succeeded with local defines;
  its built bundle contains `FLTEnableImpeller=false`.
- Dark and light native Home captures preserve the layout and effects. Mean
  RGB differences between renderers were about 1.5–1.6 out of 255 per channel.
- Hidden local-video checks advanced at least two seconds: H.264 on both
  renderers; HEVC Main10 and synthetic 4K HEVC on Skia with VideoToolbox; AV1
  on Skia with software decoding. Reported decoder drops were zero and all
  processes exited cleanly. These are short functional checks, not codec/HDR
  fidelity or sustained-performance certification.
- The full UI test run had 240 passes and 16 failures due to missing
  `appPathsProvider` bootstrap overrides. All 16 failures were reproduced
  against the original page stack in the isolated checkout.

The running developer debug app was preserved. Experimental runs used fresh
hidden profile applications and isolated data, so these measurements are not
the exact footprint of the user's live catalog, downloads or debug runtime.

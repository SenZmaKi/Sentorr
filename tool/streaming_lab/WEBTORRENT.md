# WebTorrent implementation comparison

Inspected 2026-10-02. Local checkout: `/Users/sen/Dev/webtorrent`, commit `bbcd95c0c0fa4dcf7c9a432e2ecd04a52f245996`. This is source research, not a WebTorrent-versus-libtorrent performance benchmark. No dependencies were installed and no engine changes were made for this report.

## Conclusion

WebTorrent has useful streaming policies, but its source does not establish that switching engines will shorten our 20–30 second starts. Both implementations wait for complete, verified torrent pieces and expose ordinary range-readable media to the player. Its most relevant differences are a small urgent frontier backed by broader normal-priority downloading, speed-aware peer queues, and optional HTTP web seeds. Our current lab already uses libtorrent's native time-critical picker; the clearest opportunities are in how we feed that picker and how we overlap startup phases.

## What it does

| Mechanism | WebTorrent implementation | Sentorr lab today | Implication |
| --- | --- | --- | --- |
| Streaming selection | An iterator selects its entire byte range at priority 1; waiting for a missing piece marks that piece and a small frontier critical. Frontier formula is `min(floor(1 MiB / pieceLength), 2)`, additional pieces beyond the current one. | A moving 16 MiB byte window is all priority 7, with deadlines spaced 500 ms per piece. | Separate urgently needed pieces from ordinary prefetch. Bigger read-ahead should not imply every piece is equally urgent. |
| Background selection | Unless `deselect: true`, the entire torrent starts selected at low priority. Sequential is the default strategy. | All files and pieces are deselected until a reader makes demands; work is bounded to active reader windows. | A default WebTorrent demo may already be downloading before playback starts. Compare the same selection policy before attributing speed to the engine. |
| Serving media | HTTP GET/range creates a file iterator; the iterator waits for verification and then reads the chunk store. | HTTP range → 64 KiB read → verified native piece read → memory cache → socket. | No special partial-piece playback shortcut was found. Both use progressive downloading. |
| Cancellation | Destroying the iterator removes its stream range selection. | Seek/disconnect cancels HTTP reads and releases their moving piece windows. | Broad prefetch must retain our cancellation behavior so old seeks do not compete with the new position. |
| Peer request pipeline | Per-peer target uses 0.5–1 seconds of measured throughput; block pipeline is `2 + ceil(duration * speed / blockLength)`, capped by peer `reqq` when present. | Native libtorrent handles block requests; Dart controls piece deadlines. | Do not implement a second block scheduler in Dart. Verify native queue settings and expose queue diagnostics first. |
| Slow-peer recovery | Speed ranking avoids handing work to a slow peer when a faster peer can finish it; hotswap releases reservations held by sufficiently slower peers. | Libtorrent's deadline picker also estimates peer queue time and retries stalled critical blocks. | This capability is already available through libtorrent. How we set urgency matters more than copying JS code. |
| Discovery | Trackers, DHT, local discovery and PEX (subject to privacy/runtime support). Magnet metadata fetched through `ut_metadata`. | Fresh native session per experiment; magnet metadata is acquired before selecting/playing. | Reusing a warmed session and caching metadata can remove startup work without relaxing playback readiness. |
| HTTP web seeds | Enabled by default; metadata `urlList` is added as peers. Web seed reads are HTTP ranges, still verified against torrent piece hashes. | The lab does not explicitly inject fallback web seed URLs. Native torrent metadata may already contain them. | Trusted matching web seeds can improve predictability substantially. They are additional infrastructure/sources, not a free improvement for arbitrary magnets. |
| Memory store cache | Default 20 piece slots, configurable; wraps non-memory chunk stores. | Byte-bounded 24 MiB copied-piece LRU plus native and player caches. | Different cache sizes can skew comparisons. Measure bytes, duplicate copies and total RSS rather than slot count alone. |

## Libtorrent already has the relevant native machinery

Libtorrent distinguishes sequential ordering from its time-critical picker. The latter chooses peers by estimated queue time, avoids excessively queued peers, and retries slow critical blocks using observed completion times. Its documentation warns that nonurgent requests can take bandwidth from urgent ones. That supports testing a narrow urgent frontier with controlled prefetch rather than treating a large byte window as a universal deadline policy. The current official page identifies version 2.1.0; exact behavior should be checked against our built version before changing native settings. [Official streaming implementation](https://www.libtorrent.org/streaming.html).

## Concrete evidence in our recorded startup

The existing `validation/tuning-sintel-5.local.json` records metadata ready at 1.733 s, first GET at 1.760 s, a replacement GET at 6.908 s, a tail/index GET at 11.895 s, and a replacement tail GET at 17.040 s. The old requests are cancelled at those transitions. The audit reports first progression at approximately 22.2 s despite a 5-second ready target. Those are recorded facts from one run, not a controlled causal result.

The installed MediaKit 1.2.6 source sets mpv `network-timeout` to 5 seconds (`/Users/sen/.pub-cache/hosted/pub.dev/media_kit-1.2.6/lib/src/player/native/player/real.dart:2394`); our native missing-piece wait allows 45 seconds. The approximately five-second request replacements are consistent with that timeout interfering with slow verified-piece acquisition and serialized container probes. **This remains an inference**: request replacement can also be decoder probe behavior. Test a longer player timeout and concurrent bounded header/index bootstrap against the same controlled slow seed. Increasing the timeout alone can merely delay failure, so require successful startup and unchanged cancellation responsiveness, not fewer retry events alone.

The retired Electron implementation (available at Git commit `b18f176`) is also a useful comparison: `Electron/package.json:44` uses WebTorrent `^2.5.19`; `Electron/src/backend/torrent/server/manager.ts:106` adds torrents with `deselect: true`, then `manager.ts:153` calls `file.select()`. Thus its selected file continues normal downloading beyond immediate HTTP demand. It does not rely on default whole-torrent selection. The newly cloned commit is not guaranteed identical to the previously shipped 2.5.19 package, so this report treats current source and old application policy separately.

## Most promising next experiments

These are deductions from the inspected code, not measured improvements:

1. **Separate urgency from prefetch.** Keep current and near-future pieces time-critical; give a larger bounded window ordinary priority. Derive deadline spacing from estimated media consumption, rather than always assigning 500 ms per piece. A 128 KiB piece and a 4 MiB piece cover very different playback durations. Measure startup and stalls at equal downloaded-byte budgets.
2. **Keep discovery warm.** Use one long-lived native session in the eventual application; persist its DHT state and cache verified torrent metadata. Cold metadata fetch, warm metadata cache and warm peer connections must remain separately labeled in the audit. The lab intentionally resets these on every experiment.
3. **Overlap file selection and container bootstrap.** Prefetch a small beginning and end/index probe as soon as metadata/file choice is available, while preparing the player. Do not download a large arbitrary tail: use actual container read traces and cancellation. MP4 layout can dominate apparent torrent performance.
4. **Adaptive readiness.** Reduce the initial target toward 5 seconds only when measured delivery comfortably exceeds consumption; retain a larger target for weak/inconsistent swarms. Optimize seconds lost to stalls, not just first-progress time. A 40 Mbps cap does not mean the swarm supplies 40 Mbps.
5. **Instrument native acquisition.** Split discovery, metadata, first useful byte, container probe, decode readiness and buffer target. Add useful payload rate, piece completion time, critical-piece waits and peer queue/availability diagnostics. Without that split a 20-second start does not tell us what to fix.
6. **Lower transport overhead only after measuring it.** Our path polls piece availability every 40 ms, pumps native alerts every 20 ms, copies full pieces across FFI, copies 64 KiB slices, and flushes each slice. Event-driven verified alerts and fewer bounded copies/writes are plausible CPU/latency improvements, but these millisecond operations alone do not explain a multi-second discovery wait.
7. **HTTP-assisted delivery where available.** Test a trusted matching web seed with the same torrent. For an owned catalog, CDN/HLS/DASH with optional P2P assistance offers a different reliability model; a remote torrent caching service shifts discovery/download work away from the device but adds service cost and operational dependency.

## Browser versus desktop is an important distinction

Browser WebTorrent uses WebRTC and can connect only to WebRTC-capable peers. It cannot directly use arbitrary TCP/uTP seeds listed by torrent indexes. Node/desktop environments have conventional torrent transports; a browser demo is therefore not a like-for-like replacement for native libtorrent. Web seeds and favorable curated demo swarms can make a demo feel fast. [Pinned project README](https://github.com/webtorrent/webtorrent/blob/bbcd95c0c0fa4dcf7c9a432e2ecd04a52f245996/README.md#L32-L49), [official FAQ](https://webtorrent.io/faq).

## Fair benchmark required before considering an engine switch

Use the same local generated torrent, piece length, file, independent seed, network cap/latency, HTTP consumer and startup threshold. Run sequentially with fresh caches, then separately with warm caches. Compare first frame/progression, continuous-play stalls, late/backward/rapid seek recovery, useful and redundant download bytes, and peak CPU/RSS. Add a second test with two seeds of different speeds to stress stalled critical pieces. Public swarms are supplementary because peer availability changes between runs. This research did not execute that comparison and makes no claim that WebTorrent is faster.

## Additional transport finding: uTP must be controlled in comparisons

The main investigation reports a direct pure-Dart libtorrent loopback probe, independent of MediaKit, using 8 MiB pieces and a 10 Mbps download cap: the uTP run stalled at 317 of 512 blocks, while forcing TCP completed in approximately 9 seconds. This is a reported local reproduction from the main investigation, not a benchmark executed by the author of this source comparison. It narrows that reproduction to native transfer/transport behavior rather than player readiness. It does **not** establish that uTP is universally slow, explain the underlying fault, or predict public-swarm improvement.

WebTorrent does not unconditionally use TCP. `utp-native` is an optional dependency; `lib/utp.cjs` catches a failed import and returns an empty object. `ConnPool.UTP_SUPPORT` checks whether that import exposed anything, and `index.js:85` enables uTP only when supported and not explicitly disabled. With support, IPv4 outgoing peers initially use uTP; otherwise they use TCP. The outgoing queue invokes `utp.connect`/the uTP server or `net.connect` accordingly. After exhausting reconnect retries, the code adds a TCP peer. Therefore a WebTorrent installation where the native optional dependency failed can silently differ in its effective peer transport from a libtorrent default run (apart from its logged warning).

Pinned sources: [optional native import](https://github.com/webtorrent/webtorrent/blob/bbcd95c0c0fa4dcf7c9a432e2ecd04a52f245996/lib/utp.cjs#L1-L12), [optional dependency declaration](https://github.com/webtorrent/webtorrent/blob/bbcd95c0c0fa4dcf7c9a432e2ecd04a52f245996/package.json#L119-L121), [client transport enabling](https://github.com/webtorrent/webtorrent/blob/bbcd95c0c0fa4dcf7c9a432e2ecd04a52f245996/index.js#L84-L85), [support detection](https://github.com/webtorrent/webtorrent/blob/bbcd95c0c0fa4dcf7c9a432e2ecd04a52f245996/lib/conn-pool.js#L189), [initial outgoing choice](https://github.com/webtorrent/webtorrent/blob/bbcd95c0c0fa4dcf7c9a432e2ecd04a52f245996/lib/torrent.js#L1063-L1066), [connect/reconnect/TCP fallback](https://github.com/webtorrent/webtorrent/blob/bbcd95c0c0fa4dcf7c9a432e2ecd04a52f245996/lib/torrent.js#L2121-L2173).

Libtorrent documents four independent switches: `enable_outgoing_utp`, `enable_incoming_utp`, `enable_outgoing_tcp`, and `enable_incoming_tcp`, all enabled by default on the current reference page. They control peer transports; disabling uTP peer connections does not disable UDP trackers or DHT. [Official settings reference](https://www.libtorrent.org/reference-Settings.html#enable_outgoing_utp).

Next comparison should explicitly record the negotiated transport, native-library version, optional WebTorrent uTP availability and both endpoint settings. Repeat identical TCP/uTP probes without a cap and at 10/40 Mbps, then repeat with public swarms. Preserve a separate mixed-transport run before considering a product default: TCP-only can exclude peers reachable only over uTP, so a local workaround is not automatically the best general policy.
